## Objectives

1. Execute a structured **test plan** against the deployed CFS hub & spoke environment
2. Use **Azure Network Watcher Connection Monitor** to validate end-to-end path reachability
3. Enable and review **NSG flow logs** to confirm traffic is flowing as expected
4. **Remediate** any failed tests and document the remediation log
5. Obtain **customer sign-off** (trainer acting as CFS sponsor) on the test results

<Aside type="caution" title="Customer sign-off is mandatory for B.4.1">
The B.4.1 control specifically requires **evidence of customer approval** of the test
results. In the classroom context, your **trainer acts as the CFS sponsor**. Do not skip
the sign-off step — an unsigned test plan does not satisfy B.4.1.
</Aside>

## Module B control — B.4.1

> **B.4.1 — Validation and Testing**
> The partner has conducted validation and testing of the networking solution and has
> documented the results, including evidence of customer review and acceptance of the
> test results.

The auditor checks for: a test plan with defined pass criteria, executed test results,
a remediation log for any failures, and a customer-signed acceptance.

## The CFS test scope

The test plan covers all four security layers of the CFS deployment:

| Layer | What to test |
|---|---|
| **Network segmentation** | Hub-to-spoke routing, inter-spoke isolation, Firewall policy enforcement |
| **Private networking** | DNS resolves to private IPs; no public endpoints reachable |
| **Secure access** | Bastion-only admin access; no direct SSH/RDP from internet |
| **Global delivery** | Front Door → App Gateway → private compute path; WAF blocking test payload |

## Part A — Generate the test plan

<Steps>
1. Ask the `validation-engineer` to generate the CFS test plan:
   ```
   @validation-engineer Generate a B4.1 test plan for the Contoso Financial Services
   hub & spoke deployment. Cover network segmentation, private networking, secure admin
   access, NSG flow log validation, and WAF testing. Include pass criteria for each test.
   ```

2. Review the generated test cases. Each test case must include:
   - **Test ID** (e.g. `TC-01`)
   - **Description** — what is being tested
   - **Pre-conditions** — resources that must exist
   - **Steps** — how to execute the test
   - **Expected result** (pass criteria)
   - **Actual result** (to fill in during execution)
   - **Status** (Pass / Fail / Remediated)

3. Challenge the test plan coverage:
   ```
   @challenger Review this test plan. Are all CFS security requirements from B.1.1 tested?
   Is the WAF in Prevention mode verified? Is private DNS resolution tested?
   ```

4. Fill in `evidence-templates/B4.1_TestPlan_CFS_v1.docx` with the test cases before
   execution.
</Steps>

## Part B — Enable NSG flow logs and Network Watcher

<Steps>
1. Verify Network Watcher is enabled for Sweden Central:
   ```bash
   az network watcher list -o table
   # If missing: az network watcher configure -l swedencentral -g NetworkWatcherRG --enabled true
   ```

2. Enable NSG flow logs on the hub and spoke NSGs:
   ```bash
   # Hub NSG
   az network watcher flow-log create \
     --name cfs-hub-nsg-flowlog \
     --nsg cfs-hub-nsg-swc \
     --resource-group rg-cfs-hub-swc \
     --storage-account $ST_NAME \
     --enabled true \
     --format JSON \
     --log-version 2 \
     --retention 30 \
     --traffic-analytics true \
     --workspace cfs-mgmt-law-swc
   ```
   Repeat for the spoke NSG (`cfs-app-nsg-swc` in `rg-cfs-spoke-swc`).

3. Confirm flow logs are active:
   ```bash
   az network watcher flow-log list \
     --location swedencentral -o table
   ```
</Steps>

## Part C — Connection Monitor tests

<Steps>
1. Create a Connection Monitor test group for CFS:
   ```bash
   az network watcher connection-monitor create \
     --name cfs-connection-monitor \
     --resource-group rg-cfs-hub-swc \
     --location swedencentral \
     --test-groups '[
       {
         "name": "hub-to-spoke",
         "sources": [{"resourceId": "<hub-vm-id>", "type": "AzureVM"}],
         "destinations": [{"address": "10.1.4.4", "type": "IPAddress"}],
         "testConfigurations": [{"name":"tcp-80","protocol":"Tcp","tcpConfiguration":{"port":80}}]
       }
     ]'
   ```

2. Run key test cases manually using Azure CLI or Bastion:

   **TC-01: Hub to spoke routing via Firewall**
   ```bash
   # From a hub VM (via Bastion), ping the spoke compute private IP
   ping 10.1.4.4 -c 4
   # Expected: success (Firewall allows)
   ```

   **TC-02: Spoke cannot reach spoke directly (no direct peering)**
   ```bash
   # Verify inter-spoke isolation — traffic must go via hub Firewall
   # Check Firewall logs for the flow
   az monitor activity-log list --resource-group rg-cfs-hub-swc \
     --start-time "$(date -d '1 hour ago' +%Y-%m-%dT%H:%MZ)" -o table
   ```

   **TC-03: Private DNS resolution**
   ```bash
   # Discover the dynamic Key Vault name first
   KV_NAME=$(az keyvault list -g rg-cfs-spoke-swc --query '[0].name' -o tsv)
   # From spoke compute (via Bastion)
   nslookup ${KV_NAME}.vault.azure.net
   # Expected: 10.1.1.x private IP (not the public Azure IP)
   ```

   **TC-04: No public access to Key Vault**
   ```bash
   # From outside the VNet (e.g. Cloud Shell in a separate subscription)
   curl -s "https://${KV_NAME}.vault.azure.net/keys?api-version=7.4"
   # Expected: 403 Forbidden (network ACL denies public access)
   ```

   **TC-05: Bastion is the only admin path**
   ```bash
   # Attempt direct SSH to spoke VM public IP
   ssh azureuser@<spoke-vm-private-ip>
   # Expected: connection refused (no public IP, no direct port 22 from internet)
   ```

   **TC-06: WAF blocks OWASP test payload**
   ```bash
   AFD_ENDPOINT="<your-front-door-hostname>"
   curl -I "https://${AFD_ENDPOINT}/?<script>alert(1)</script>"
   # Expected: HTTP 403 from WAF (XSS rule match)
   ```

3. Record **Actual result** and **Status** for each test case in the test plan document.
</Steps>

## Part D — Review NSG flow logs and Traffic Analytics

<Steps>
1. Wait 5–10 minutes after tests for flow logs to populate, then review in Azure Portal:
   **Network Watcher → Traffic Analytics → select the Log Analytics workspace**

2. Confirm in Traffic Analytics:
   - Traffic from spoke to internet is shown via Hub Firewall (not direct)
   - Bastion access appears in allowed flows
   - Any blocked flows show as denied with the NSG rule that blocked them

3. Ask the agent to interpret results:
   ```
   @validation-engineer Review these NSG flow log findings. Are there any unexpected
   allowed flows that should be blocked? Any denied flows that indicate misconfiguration?
   ```
</Steps>

## Part E — Remediate failures

<Steps>
1. For any failed test cases, document the remediation in the test plan:
   ```
   @validation-engineer TC-03 failed: DNS resolves to public IP instead of private.
   What is the most likely root cause and fix for a private endpoint DNS configuration?
   ```

2. Apply the fix (e.g. add missing Private DNS Zone VNet link), re-run the test, and
   update the status to **Remediated**.

3. Ensure all test cases are **Pass** or **Remediated** before proceeding to sign-off.
</Steps>

## Part F — Customer sign-off (MANDATORY)

<Aside type="caution" title="This step is required for B.4.1">
Do not skip this. An unsigned or unacknowledged test results document does **not** satisfy
B.4.1. In the classroom, your **trainer** plays the CFS sponsor role.
</Aside>

<Steps>
1. Prepare the sign-off document:
   ```
   @evidence-author Prepare B4.1_SignOff_CFS_v1.docx. Summarise the test results:
   X tests passed, Y remediated, 0 outstanding failures. Include the test execution date,
   environment (swedencentral), and a signature block for the CFS sponsor.
   ```

2. Hand the document to your trainer (CFS sponsor). The trainer reviews and:
   - Confirms all test cases are Pass or Remediated
   - Signs (or prints name + date) in the signature block
   - Notes any conditional acceptances or follow-up items

3. Scan or photograph the signed document and attach it to `B4.1_SignOff_CFS_v1.docx`.
   In a digital-only workflow, a named acknowledgement in a Teams/email thread is acceptable
   — attach the thread screenshot.

4. Confirm the challenger is satisfied:
   ```
   @challenger Review the sign-off document. Is the customer acceptance unambiguous?
   Are all test outcomes clearly linked to the B.4.1 test plan?
   ```
</Steps>
