## Part A — Verify Private Endpoints and Private DNS resolution

The Key Vault and Storage account names are generated from `uniqueString(subscription().id)`.
Discover them before running DNS tests:

```bash
# Discover the dynamic names
KV_NAME=$(az keyvault list -g rg-cfs-spoke-swc --query '[0].name' -o tsv)
ST_NAME=$(az storage account list -g rg-cfs-spoke-swc --query '[0].name' -o tsv)
echo "Key Vault: $KV_NAME"
echo "Storage:   $ST_NAME"
```

<Steps>
1. Verify private endpoints exist in the spoke:
   ```bash
   az network private-endpoint list -g rg-cfs-spoke-swc -o table
   ```
   Expected: one endpoint for Key Vault and one for Storage.

2. Ask the `iac-engineer` to explain the configuration:
   ```
   @iac-engineer Explain how infra/bicep/modules/key-vault.bicep and
   infra/bicep/modules/private-dns.bicep together ensure Key Vault is
   unreachable from the public internet but resolvable inside the spoke VNet.
   ```

3. Verify DNS resolution from inside the spoke (use Bastion to open a shell on `cfs-app-vm-swc`,
   or use Cloud Shell inside the spoke VNet):
   ```bash
   # Key Vault — must resolve to 10.1.1.x (privateEndpoints subnet), not a public IP
   nslookup ${KV_NAME}.vault.azure.net
   # Storage — must resolve to 10.1.1.x
   nslookup ${ST_NAME}.blob.core.windows.net
   ```

4. Verify no public network access is enabled on the services:
   ```bash
   az keyvault show -n $KV_NAME \
     --query 'properties.networkAcls.defaultAction' -o tsv
   # Expected: Deny
   az storage account show -n $ST_NAME \
     --query 'publicNetworkAccess' -o tsv
   # Expected: Disabled
   ```
</Steps>

## Part B — Verify private compute (no public IPs)

<Steps>
1. Verify no public IPs are attached to compute VMs:
   ```bash
   az vm list -g rg-cfs-spoke-swc \
     --query '[].{name:name, location:location}' -o table
   az network public-ip list -g rg-cfs-spoke-swc -o table
   # Expected: empty list — no public IPs in the spoke resource group
   ```

2. Confirm Bastion is the only admin path into the VM:
   - Navigate to `cfs-app-vm-swc` in Azure Portal
   - Select **Connect → Bastion**
   - Confirm SSH connects successfully over the private path (no public IP required)

3. Verify the VM NIC is in the `10.1.0.0/24` workload subnet:
   ```bash
   VM_NIC=$(az vm show -n cfs-app-vm-swc -g rg-cfs-spoke-swc \
     --query 'networkProfile.networkInterfaces[0].id' -o tsv)
   az network nic show --ids $VM_NIC \
     --query 'ipConfigurations[0].privateIPAddress' -o tsv
   # Expected: 10.1.0.x
   ```
</Steps>

## Part C — Inspect the internal Load Balancer

<Steps>
1. Verify the Load Balancer is internal Standard SKU:
   ```bash
   az network lb show -n cfs-app-ilb-swc -g rg-cfs-spoke-swc \
     --query '{sku:sku.name, frontendIp:frontendIPConfigurations[0].privateIPAddress}' -o json
   # Expected: sku: Standard, frontendIp: 10.1.3.10
   ```

2. Ask the agent about the design:
   ```
   @iac-engineer Why does CFS use an internal Load Balancer in front of the compute tier?
   How does this interact with the Application Gateway WAF?
   ```
</Steps>

## Part D — Inspect Application Gateway + WAF v2

<Steps>
1. Verify WAF policy is in Prevention mode with CRS 3.2:
   ```bash
   az network application-gateway waf-config show \
     --gateway-name cfs-app-agw-swc -g rg-cfs-spoke-swc \
     --query '{firewallMode:firewallMode, ruleSetType:ruleSetType, ruleSetVersion:ruleSetVersion}' -o json
   # Expected: firewallMode: Prevention, ruleSetVersion: 3.2
   ```

2. Verify the backend pool points to the internal Load Balancer:
   ```bash
   az network application-gateway address-pool list \
     --gateway-name cfs-app-agw-swc -g rg-cfs-spoke-swc -o table
   # Expected: backend IP should be 10.1.3.10 (ILB frontend)
   ```

3. **(Optional hands-on — WAF custom rule)**: Add a custom WAF rule to block a test header:
   ```bash
   # Add a custom rule that blocks requests with header X-Test-Block: true
   az network application-gateway waf-policy custom-rule create \
     --policy-name cfsappagwwafswc \
     --resource-group rg-cfs-spoke-swc \
     --name BlockTestHeader \
     --priority 100 \
     --rule-type MatchRule \
     --action Block \
     --match-conditions '[{"matchVariables":[{"variableName":"RequestHeaders","selector":"X-Test-Block"}],"operator":"Contains","matchValues":["true"]}]'
   ```
   Test it with `curl -H "X-Test-Block: true" http://<appgw-frontend-ip>/` — expected: HTTP 403.
   Remove the custom rule when done.
</Steps>

## Part E — Test Azure Front Door

<Steps>
1. Discover the Front Door endpoint hostname:
   ```bash
   AFD_HOST=$(az afd endpoint list \
     --profile-name cfs-edge-afd-swc \
     -g rg-cfs-spoke-swc \
     --query '[0].hostName' -o tsv)
   echo "Front Door endpoint: $AFD_HOST"
   ```

2. Test end-to-end delivery:
   ```bash
   curl -I "https://${AFD_HOST}"
   # Expected: HTTP 200 or 301 from Application Gateway backend
   ```

3. Verify the Front Door WAF policy is active:
   ```bash
   az afd security-policy list \
     --profile-name cfs-edge-afd-swc -g rg-cfs-spoke-swc -o table
   ```

4. Ask the agent about the origin configuration:
   ```
   @iac-engineer How does infra/bicep/modules/front-door.bicep connect Front Door to
   the Application Gateway? Why is Private Link origin required (not a public IP origin)?
   ```
</Steps>
