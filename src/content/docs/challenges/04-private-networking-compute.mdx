## Objectives

Complete the CFS networking deployment by adding:

1. **Private Endpoints + Private DNS Zones** for Azure Key Vault, Storage, and SQL (Private Link)
2. **Private compute** — workload VMs with no public IPs, accessible only via Bastion
3. **Azure Load Balancer** — internal, distributing across compute instances
4. **Application Gateway + WAF (v2)** — application-layer protection at the spoke edge
5. **Azure Front Door Premium + WAF policy** — secure global delivery for CFS's external-facing app

After this challenge, the CFS deployment uses **≥7 native Azure networking services**,
satisfying **B.3.2**.

## Module B control — B.3.2

## Part A — Deploy Private Endpoints and Private DNS

<Steps>
1. Ask the `iac-engineer` to review the private endpoint configuration:
   ```
   @iac-engineer Review infra/bicep/private-endpoints/main.bicep for the CFS deployment.
   Confirm Key Vault, Storage, and SQL each have a private endpoint in cfs-app-vnet-swc,
   a private DNS zone linked to the spoke VNet, and no public network access enabled.
   ```

2. Run `what-if` validation for private endpoints:
   ```bash
   az deployment group what-if \
     --resource-group rg-cfs-app-swc \
     --template-file infra/bicep/private-endpoints/main.bicep \
     --parameters infra/bicep/parameters/lab.bicepparam
   ```

3. Deploy:
   ```bash
   gh workflow run deploy.yml -f component=private-endpoints
   gh run watch
   ```

4. Verify DNS resolution from a test VM (or Cloud Shell in the spoke):
   ```bash
   # Key Vault
   nslookup cfs-kv-swc.vault.azure.net
   # Should resolve to a 10.1.x.x private IP, NOT the public vault.azure.net IP
   ```

5. Verify no public network access is enabled on the services:
   ```bash
   az keyvault show -n cfs-kv-swc --query 'properties.networkAcls.defaultAction' -o tsv
   # Expected: Deny
   az storage account show -n cfsstswc --query 'publicNetworkAccess' -o tsv
   # Expected: Disabled
   ```
</Steps>

## Part B — Deploy private compute (no public IPs)

<Steps>
1. Deploy private compute:
   ```bash
   gh workflow run deploy.yml -f component=compute
   gh run watch
   ```

2. Verify no public IPs are attached to compute:
   ```bash
   az vm list -g rg-cfs-app-swc --query '[].{name:name,publicIpAddress:networkProfile}' -o table
   az network public-ip list -g rg-cfs-app-swc -o table
   # Expected: no public IPs in the spoke resource group
   ```

3. Test private access via Bastion:
   - Navigate to the VM in Azure Portal
   - Select **Connect → Bastion**
   - Confirm SSH/RDP connects successfully over the private path
</Steps>

## Part C — Deploy Azure Load Balancer (internal)

<Steps>
1. Verify the Load Balancer parameters:
   ```
   @iac-engineer Review the internal Load Balancer config in infra/bicep/compute/main.bicep.
   Confirm it is an internal SKU Standard, frontend IP is from the app spoke subnet,
   and health probes target port 80 on the backend VMs.
   ```

2. Deploy:
   ```bash
   gh workflow run deploy.yml -f component=compute
   # Load Balancer is co-deployed with compute
   ```

3. Verify:
   ```bash
   az network lb show -n cfs-app-ilb-swc -g rg-cfs-app-swc \
     --query '{sku:sku.name, frontendIp:frontendIPConfigurations[0].privateIPAddress}' -o json
   ```
</Steps>

## Part D — Deploy Application Gateway + WAF v2

<Steps>
1. Review the App Gateway parameters:
   ```
   @iac-engineer Review infra/bicep/appgateway/main.bicep.
   Confirm WAF mode is Prevention (not Detection), CRS 3.2 ruleset is active,
   the App Gateway subnet is dedicated (no other resources), and
   the backend pool points to the internal Load Balancer frontend IP.
   ```

2. Run `what-if`:
   ```bash
   az deployment group what-if \
     --resource-group rg-cfs-app-swc \
     --template-file infra/bicep/appgateway/main.bicep \
     --parameters infra/bicep/parameters/lab.bicepparam
   ```

3. Deploy:
   ```bash
   gh workflow run deploy.yml -f component=appgateway
   gh run watch
   ```

4. Verify WAF policy is in Prevention mode:
   ```bash
   az network application-gateway waf-config show \
     --gateway-name cfs-app-agw-swc -g rg-cfs-app-swc \
     --query '{firewallMode:firewallMode, ruleSetType:ruleSetType, ruleSetVersion:ruleSetVersion}' -o json
   # Expected: firewallMode: Prevention, ruleSetVersion: 3.2
   ```
</Steps>

## Part E — Deploy Azure Front Door Premium + WAF policy

<Steps>
1. Review the Front Door configuration:
   ```
   @iac-engineer Review infra/bicep/frontdoor/main.bicep.
   Confirm Front Door is Premium SKU, WAF policy is in Prevention mode,
   the origin is the Application Gateway, and Private Link origin is used
   (no direct public endpoint from Front Door to backend).
   ```

2. Deploy:
   ```bash
   gh workflow run deploy.yml -f component=frontdoor
   gh run watch
   ```

3. Test end-to-end delivery:
   ```bash
   AFD_ENDPOINT=$(az afd endpoint show \
     --profile-name cfs-afd-profile \
     --endpoint-name cfs-app-endpoint \
     -g rg-cfs-app-swc \
     --query hostName -o tsv)
   curl -I "https://${AFD_ENDPOINT}"
   # Expected: HTTP 200 or 301 from Application Gateway backend
   ```

4. Verify WAF policy is active on Front Door:
   ```bash
   az afd security-policy list \
     --profile-name cfs-afd-profile -g rg-cfs-app-swc -o table
   ```
</Steps>

<Aside type="tip" title="Trainer tip">
A common pitfall is having the Application Gateway use public network access to reach the
backend. For CFS, the backend pool must point to the internal Load Balancer or directly to
private compute. If Front Door cannot reach the App Gateway privately, the Front Door
Private Link to App Gateway feature is required. See
[Solution 04](../../solutions/04-private-networking-compute/) for the correct Bicep pattern.
</Aside>
