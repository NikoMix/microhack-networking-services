## Objectives

Complete the CFS networking deployment by adding:

1. **Private Endpoints + Private DNS Zones** for Azure Key Vault and Storage (Private Link)
2. **Private compute** — workload VMs with no public IPs, accessible only via Bastion
3. **Azure Load Balancer** — internal, distributing across compute instances
4. **Application Gateway + WAF (v2)** — application-layer protection at the spoke edge
5. **Azure Front Door Premium + WAF policy** — secure global delivery for CFS's external-facing app

After this challenge, the CFS deployment uses **≥7 native Azure networking services**,
satisfying **B.3.2**.

## Part A — Verify Private Endpoints and Private DNS

<Steps>
1. Ask the `iac-engineer` to review the deployed private endpoint configuration:
   ```
   @iac-engineer Review infra/bicep/modules/private-dns.bicep, key-vault.bicep, and storage.bicep
   for the CFS deployment. Confirm Key Vault and Storage each have a private endpoint in
   cfs-app-vnet-swc, a private DNS zone linked to the spoke VNet, and no public network access.
   ```

2. Confirm the private endpoints exist (deployed by the `spoke` component in Challenge 03):
   ```bash
   az network private-endpoint list -g rg-cfs-spoke-swc -o table
   # Expected: a private endpoint for Key Vault and one for Storage
   ```

3. Verify DNS resolution from a test VM (or Cloud Shell in the spoke):
   ```bash
   # Key Vault
   nslookup cfs-kv-swc.vault.azure.net
   # Should resolve to a 10.1.x.x private IP, NOT the public vault.azure.net IP
   ```

4. Verify no public network access is enabled on the services:
   ```bash
   az keyvault show -n cfs-kv-swc --query 'properties.networkAcls.defaultAction' -o tsv
   # Expected: Deny
   az storage account show -n cfsstswc --query 'publicNetworkAccess' -o tsv
   # Expected: Disabled
   ```
</Steps>

## Part B — Verify private compute (no public IPs)

<Steps>
1. Confirm the private VM was deployed by the `spoke` component (Challenge 03) and has no public IP:
   ```bash
   az vm list -g rg-cfs-spoke-swc -o table
   az network public-ip list -g rg-cfs-spoke-swc -o table
   # Expected: no public IPs in the spoke resource group
   ```

2. Test private access via Bastion:
   - Navigate to the VM in Azure Portal
   - Select **Connect → Bastion**
   - Confirm SSH/RDP connects successfully over the private path
</Steps>

## Part C — Verify the internal Azure Load Balancer

<Steps>
1. Review the internal Load Balancer configuration:
   ```
   @iac-engineer Review the internal Load Balancer config in infra/bicep/modules/load-balancer.bicep.
   Confirm it is an internal Standard SKU, the frontend IP is from the app spoke subnet,
   and health probes target port 80 on the backend VMs.
   ```

2. Verify the Load Balancer (deployed by the `spoke` component in Challenge 03):
   ```bash
   az network lb show -n cfs-app-ilb-swc -g rg-cfs-spoke-swc \
     --query '{sku:sku.name, frontendIp:frontendIPConfigurations[0].privateIPAddress}' -o json
   ```
</Steps>

## Part D — Deploy the edge (Application Gateway + WAF and Front Door + WAF)

<Aside type="note" title="One `edge` deploy covers both">
The `edge` component deploys **both** the Application Gateway + WAF v2 and Azure Front Door
Premium + WAF in a single run. You verify the App Gateway here in Part D and Front Door in Part E.
</Aside>

<Steps>
1. Review the App Gateway and Front Door parameters:
   ```
   @iac-engineer Review infra/bicep/modules/app-gateway.bicep and front-door.bicep.
   Confirm App Gateway WAF mode is Prevention (not Detection) with CRS 3.2, the App Gateway
   subnet is dedicated, the backend points to the internal Load Balancer frontend IP, and
   Front Door is Premium with a Prevention-mode WAF policy using a Private Link origin.
   ```

2. Preview the edge deployment with a safe what-if (gated by the `what-if-review` skill):
   ```bash
   gh workflow run deploy.yml -f component=edge -f whatIfOnly=true
   gh run watch
   ```

3. Deploy the edge:
   ```bash
   gh workflow run deploy.yml -f component=edge
   gh run watch
   ```

4. Verify the App Gateway WAF policy is in Prevention mode:
   ```bash
   az network application-gateway waf-config show \
     --gateway-name cfs-app-agw-swc -g rg-cfs-spoke-swc \
     --query '{firewallMode:firewallMode, ruleSetType:ruleSetType, ruleSetVersion:ruleSetVersion}' -o json
   # Expected: firewallMode: Prevention, ruleSetVersion: 3.2
   ```
</Steps>

## Part E — Verify Azure Front Door Premium + WAF policy

<Aside type="note" title="Deployed by the `edge` component">
Front Door was deployed alongside the Application Gateway by the `edge` component in Part D.
This part verifies it end to end.
</Aside>

<Steps>
1. Test end-to-end delivery:
   ```bash
   AFD_ENDPOINT=$(az afd endpoint show \
     --profile-name cfs-edge-afd-swc \
     --endpoint-name cfs-edge-afd-swc-ep \
     -g rg-cfs-spoke-swc \
     --query hostName -o tsv)
   curl -I "https://${AFD_ENDPOINT}"
   # Expected: HTTP 200 or 301 from the Application Gateway backend
   ```

2. Verify the WAF policy is active on Front Door:
   ```bash
   az afd security-policy list \
     --profile-name cfs-edge-afd-swc -g rg-cfs-spoke-swc -o table
   ```
</Steps>

<Aside type="tip" title="Trainer tip">
A common pitfall is having the Application Gateway use public network access to reach the
backend. For CFS, the backend pool must point to the internal Load Balancer or directly to
private compute. If Front Door cannot reach the App Gateway privately, the Front Door
Private Link to App Gateway feature is required. See
[Solution 04](../../solutions/04-private-networking-compute/) for the correct Bicep pattern.
</Aside>
