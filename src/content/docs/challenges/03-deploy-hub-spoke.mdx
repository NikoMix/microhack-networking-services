<Aside type="danger" title="🚀 DO THIS FIRST — preview, then kick off the full deploy">
A **single** GitHub Actions run deploys the entire CFS hub & spoke stack (9 Azure networking
services, one idempotent Bicep file). The VPN Gateway is the long pole (~30–45 min). Your
first two actions are:

```bash
# 1 — Preview only (takes ~5 min; review the output with the agents)
gh workflow run deploy.yml -f whatIfOnly=true
gh run watch

# 2 — Once the preview looks good, kick off the real deploy
gh workflow run deploy.yml -f whatIfOnly=false
# Don't wait — continue reading while it provisions in the background.
```

Then jump to Part 0 to review the what-if output while the stack deploys.
</Aside>

## Objectives

Deploy the complete CFS secure hub & spoke landing zone. A single call to
`infra/bicep/main.bicep` with `infra/bicep/parameters/lab.bicepparam` provisions all
nine networking services in dependency order:

1. **Hub VNet** (`cfs-hub-vnet-swc`) — subnets, UDRs, NSGs
2. **Azure Firewall Premium** (`cfs-hub-afw-swc`) — central egress and east-west segmentation
3. **Azure Bastion Standard** (`cfs-hub-bas-swc`) — private admin access, no public IPs on compute
4. **VPN Gateway** (`cfs-hub-vpngw-swc`) — hybrid connectivity to CFS branches
5. **Spoke VNet** (`cfs-app-vnet-swc`) — with UDRs, NSGs, and bidirectional peering
6. **Private DNS zones** — linked to spoke for Key Vault and Storage resolution
7. **Key Vault + Storage** — private endpoint, no public network access
8. **Private compute VM** (`cfs-app-vm-swc`) + internal Load Balancer (`cfs-app-ilb-swc`)
9. **Application Gateway + WAF** (`cfs-app-agw-swc`) + **Azure Front Door** (`cfs-edge-afd-swc`)

**Challenge 04** is dedicated to verifying and exploring all these services.

This challenge satisfies **B.3.1** (scenario implementation) and begins evidence for
**B.3.2** (≥5 native Azure networking services). Challenge 04 completes the B.3.2 count.

## Part A — Understand the address space and subnet layout

While the deployment runs, review the CFS address plan from `main.bicep`:

| VNet | Address space | Subnets |
|---|---|---|
| `cfs-hub-vnet-swc` | `10.0.0.0/16` | AzureFirewallSubnet `10.0.0.0/26` · AzureBastionSubnet `10.0.1.0/26` · GatewaySubnet `10.0.2.0/27` |
| `cfs-app-vnet-swc` | `10.1.0.0/16` | workload `10.1.0.0/24` · privateEndpoints `10.1.1.0/24` · appGateway `10.1.2.0/24` · loadBalancer `10.1.3.0/24` |

The hub route table forces all spoke egress through the Firewall private IP (`10.0.0.4`).
The GatewaySubnet must **not** have a default route pointing to the Firewall — this would
break BGP routing.

<Steps>
1. Open `infra/bicep/parameters/lab.bicepparam` to review the deployment parameters.

2. Ask the agent to explain the design decision:
   ```
   @iac-engineer Explain the hub-spoke address design in infra/bicep/main.bicep.
   Why is the GatewaySubnet excluded from the spoke-bound UDR?
   ```
</Steps>

## Part B — Monitor and verify the deployment

<Steps>
1. Monitor the running deployment:
   ```bash
   gh run watch
   ```
   The full run typically completes in **50–65 minutes** (VPN Gateway is the slowest resource).

2. Once the workflow shows `completed`, verify hub resources:
   ```bash
   az network vnet list -g rg-cfs-hub-swc -o table
   az network firewall list -g rg-cfs-hub-swc -o table
   az network bastion list -g rg-cfs-hub-swc -o table
   ```

3. Confirm the UDR forces spoke egress to the Firewall:
   ```bash
   az network route-table route list \
     --route-table-name cfs-hub-rt-swc -g rg-cfs-hub-swc -o table
   # Expected: 0.0.0.0/0 → 10.0.0.4 (Firewall private IP)
   ```
</Steps>

## Part C — Verify spoke and VNet peering

<Steps>
1. Verify spoke VNet and peering:
   ```bash
   az network vnet list -g rg-cfs-spoke-swc -o table
   az network vnet peering list \
     --vnet-name cfs-hub-vnet-swc -g rg-cfs-hub-swc -o table
   az network vnet peering list \
     --vnet-name cfs-app-vnet-swc -g rg-cfs-spoke-swc -o table
   ```
   Both peerings should show state `Connected`.

2. Confirm the spoke route table forces egress through the hub Firewall (UDR):
   ```bash
   az network route-table route list \
     --route-table-name cfs-app-rt-swc -g rg-cfs-spoke-swc -o table
   ```
</Steps>

## Part D — Validate the VPN Gateway

<Aside type="note" title="Gateway timing">
If the gateway is still provisioning, continue to Part E (evidence) and return here once
`gh run watch` shows the deployment as **completed**.
</Aside>

<Steps>
1. Verify the VPN Gateway is provisioned:
   ```bash
   az network vnet-gateway show \
     -n cfs-hub-vpngw-swc -g rg-cfs-hub-swc \
     --query '{name:name, provisioningState:provisioningState, sku:sku.name}' -o json
   ```
   Expected: `provisioningState: Succeeded`.

2. Note the gateway public IP for the implementation plan artifact.
</Steps>

## Validation checklist

| Check | Command / Portal |
|---|---|
| Hub VNet and spoke VNet exist in Sweden Central | `az network vnet list -o table` |
| VNet peering is `Connected` both ways | `az network vnet peering list` |
| Azure Firewall is `Succeeded` | `az network firewall list -g rg-cfs-hub-swc` |
